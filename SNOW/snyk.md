|        1 | **A03 — Software Supply Chain Failures**        |                        🟡 |             ✅ | Snowflake scans **Runtime images** daily for vulnerabilities and addresses High/Critical CVEs by releasing new runtime versions. Snowflake also provides verified base runtime packages, but that is not the same as full dependency governance for customer-added packages. ([Snowflake Documentation][1]) | Snyk is strong here: open-source dependency scanning, transitive dependency visibility, CVE detection, license risk, remediation guidance, PR/CI workflow, and SBOM support. For Python code scanning, Snyk Code supports `.py` files, so notebook code must be exported/synced into source control. ([Snyk User Docs][2]) | If notebooks live only inside Snowsight and dependencies are installed ad hoc, Snyk may not see the code or the full dependency tree. It will not reliably stop a developer from writing unsafe dynamic SQL such as `session.sql(f"...{user_input}")`. OWASP describes injection as untrusted input being sent to an interpreter such as a database, browser, or command line. ([OWASP Foundation][3])                          | Snyk Code can help identify SQL injection, command injection, code injection, unsafe deserialization, and related patterns in Python source files, assuming the code is available to scan.                                                                                                                                 | Snyk may not understand every business-specific data path, allowed input source, or Snowpark-specific safe wrapper. Snowflake does not know whether the query logic is safe by business design.                                           | Create a **secure query standard**: prohibit f-string SQL construction, require parameterized queries or allowlisted query builders, add Semgrep/Snyk custom rules for `session.sql(f"")`, `eval`, `exec`, `subprocess`, unsafe URL/query construction, and require negative tests for malicious input.                           |

([Snowflake Documentation][4])                                                                                                                                                              | Snyk can help detect weak crypto patterns, hardcoded secrets, bad TLS verification, insecure randomness, and unsafe use of cryptographic APIs in Python code.                                                                                                                                                              | Neither Snowflake nor Snyk fully manages the full crypto lifecycle: key ownership, rotation, approved algorithms, certificate validation policy, and exceptions.                                                                          | Define a **crypto and secret-handling standard**: no hardcoded secrets, no `verify=False`, no MD5/SHA1 for security use, no custom encryption, secrets only in Snowflake Secrets / Delinea / Azure Key Vault, annual or risk-based rotation, and AppSec approval for exceptions.                                                  |

([Snowflake Documentation][5])                                                                                                                                       | Snyk can help catch code-level problems such as hardcoded credentials, insecure certificate validation, and some authentication implementation weaknesses. | **Snowflake secures the platform.**     | Snowflake native controls reduce platform, runtime, identity, and configuration risk.                                                                                   |
| **Snyk secures the development layer.** | Snyk helps close code, dependency, CVE, license, and SBOM gaps that Snowflake native controls do not fully cover.                                                       |
