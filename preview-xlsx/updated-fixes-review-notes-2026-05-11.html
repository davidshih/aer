Findings

PriorityLocationIssueRecommendation
P1 test/e2e/smoke.test.ts:26 The E2E test computes repoRoot from __dirname. After bundling to out-e2e/smoke.test.js, __dirname points at out-e2e, so path.resolve(__dirname, '..', '..') resolves to the parent workspace directory, not this extension root. The test therefore opens a likely nonexistent test/fixtures/multi-sheet.xlsx. Because it only asserts the active tab viewType, this can pass while the parser shows an error in the webview. Pass the real repo root from runE2E.js through an environment variable or esbuild define, assert fs.existsSync(fixture) before vscode.openWith, and ideally add a parse-success signal or use extension-host-visible state so the test is not tab-only.
P1 test/e2e/runE2E.js, package.json npm run test:e2e does not build the extension before launching VS Code. It passes in a warmed workspace because dist/ already exists, but a fresh checkout can test stale or missing output. Build the extension inside runE2E.js or change the script to run npm run build first.
P2 src/parsers/xlsx.ts, README.md The ignoreNodes list now uses realistic worksheet node names, and the README correctly says file-size cap is the main DoS backstop. This resolves the earlier fake-confidence issue. Keep this wording. Do not describe the full ExcelJS loader as bounded parsing.
P2 package.json The original security posture talked about exact dependency pins, but new dev dependencies use caret ranges. The lockfile pins the current install, so this is not blocking, but npm install can still move versions. Prefer exact versions for dev tooling too, especially jsdom, because this exact area just caused a runner break.

Summary

The core phase 2 fixes are much healthier now: unit, security, CSP, rendering, audit, build, and type checks pass. The remaining meaningful gap is E2E signal quality: it currently proves activation and custom editor tab registration, but not that the intended fixture was opened or parsed successfully.
